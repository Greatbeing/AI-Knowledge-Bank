# 第一部分：项目章程

## 1. 项目使命

让全球开发者生态中有价值的 AI 能力，能够被普通人发现、理解、可信地使用，并在真实任务中持续改进。

AI Knowledge Bank 不是简单的 AI 工具导航站、代码仓库镜像或静态知识门户。它是连接能力创造者与能力使用者的产品层：开发者保留原有 GitHub 工作方式，普通用户通过自然语言表达目标，由平台承担发现、解释、匹配、组合、执行治理和结果验证的复杂性。

## 2. 核心产品定义

**AI Knowledge Bank 是面向普通用户的 AI 能力分发与编排平台。**

用户提出要完成的任务，平台将：
1. 理解目标、上下文、约束和成功标准；
2. 从可信来源发现候选知识、工具、Agent 和工作流；
3. 判断适用性、兼容性、证据、风险和使用成本；
4. 生成可解释、可检查的任务计划；
5. 在授权和安全边界内调用能力；
6. 评估结果是否满足任务标准；
7. 沉淀反馈、执行证据和可复用经验。

**最终交付单位是用户完成的任务，而不是被浏览的工具条目。**

## 3. 要解决的问题

### 普通用户侧
- 不知道全球 AI 能力在哪里；
- 看不懂 Repository、源码、依赖、API、MCP 和 Agent 配置；
- 难以判断工具宣传是否可信、是否适合自己的任务；
- 需要自己拼接多个工具，学习成本高；
- 使用失败后缺乏诊断、替代方案和可追溯证据。

### 开发者侧
- 能力散落在不同仓库、格式和生态中；
- 项目说明、接口、限制和测试标准不统一；
- 能力被发现和复用的机会有限；
- 使用反馈难以转化为可维护的改进；
- 缺乏跨仓库、跨工具的能力发现与兼容层。

## 4. 目标用户

| 用户 | 核心任务 | 平台价值 |
| --- | --- | --- |
| 普通用户 | 用自然语言完成工作、学习、研究和创作 | 隐藏技术复杂度，给出可理解、可控的结果 |
| 专业用户 | 在特定领域组合可靠能力 | 可追溯的专业工作流、证据和质量控制 |
| 开发者 / 能力作者 | 发布、维护和分发能力 | 统一描述、来源归属、验证反馈和使用触达 |
| 审核者 / 专家 | 审查质量、安全、许可与适用边界 | 可审计的评估、证据和治理机制 |
| 组织客户 | 管理内部能力和受控执行 | 私有来源、权限隔离、审计和策略管理（后续阶段） |

## 5. 产品原则

1. **Task-first, not tool-first**：从用户目标开始，不要求用户先选择工具。
2. **Hide complexity, preserve control**：隐藏工程复杂度，但保留知情、授权、暂停和撤销能力。
3. **GitHub-native, source-portable**：GitHub 是首要内容来源，但平台内部使用标准化连接器，不把架构锁死在单一供应商。
4. **Evidence over popularity**：星标、下载量和营销文案不能替代任务级验证证据。
5. **Explainable orchestration**：解释为何选择能力、如何组合、将访问什么数据、产生什么副作用。
6. **Safe by default**：发现不等于信任，信任不等于执行授权。
7. **Composable capabilities**：能力必须尽可能有明确输入、输出、依赖、限制和评估标准。
8. **Reversible decisions**：高风险操作需要审批、日志、停止机制和可行的回滚方案。
9. **Open ecosystem, fair attribution**：尊重原作者、许可证、版本和来源，不把第三方成果冒充平台原创。
10. **Measure outcomes**：以任务成功率、用户时间节省、质量、成本和安全事件衡量价值。

## 6. 范围与非目标

长期范围：
- 多来源能力发现，首期以公开 GitHub 仓库为主；
- 知识、工具、Agent、工作流、模型适配器、案例和评测数据集的统一目录；
- 自然语言任务理解、能力检索、排序和组合；
- Cognitive Engine 任务规划、路由、执行跟踪和评估；
- 受控运行时和可审计权限；
- 证据、反馈、社区贡献和能力生命周期；
- 面向普通用户的 Web / Mobile 体验。

首期非目标：
- 运行任意 GitHub 代码；
- 替代 GitHub 的源码托管与协作功能；
- 一次性接入所有模型、Agent 框架和插件；
- 在检索质量未验证前追求庞大目录规模；
- 以自动化为由绕过用户审批；
- 将所有动态业务状态写入 Git；
- 先建设复杂商业市场、代币或创作者分成体系。

## 7. 成功定义

平台成功不是收录了多少仓库，而是普通用户能否在不打开 GitHub、不安装依赖、不配置 API 的情况下，可靠完成原本难以完成的任务。

核心指标：
- End-to-end Task Success Rate；
- Time to First Useful Result；
- 无需开发者配置即可完成任务的用户比例；
- 推荐接受率与执行完成率；
- 能力证据覆盖率和过期率；
- 重复使用率与跨用户复用率；
- 每次成功任务成本、延迟和失败率；
- 高风险操作审批合规率、安全事件率。

所有指标必须定义分母、时间窗口、数据来源和排除规则，禁止只展示缺乏口径的累计数字。

# 第二部分：产品需求（PRD）

## 8. 核心体验目标

普通用户进入平台后，不需要理解 GitHub、代码仓库、Prompt 工程、API、MCP 或 Agent 框架。首页首先回答：

> 你想完成什么？

平台负责把自然语言目标转化为可执行、可解释、可验证的任务流程。

## 9. 核心用户旅程

1. 用户用自然语言描述任务。
2. 系统识别任务类型、目标、输入、约束和成功标准。
3. 如缺少关键条件，只提出最少且必要的澄清问题。
4. 系统检索候选能力，并检查来源、版本、许可、兼容性和证据。
5. 系统展示推荐方案：预计步骤、使用能力、数据访问、成本/耗时范围、风险和限制。
6. 用户确认；涉及敏感数据或外部副作用时进行单独授权。
7. 系统执行任务并显示进度。
8. 系统交付结果、来源、执行摘要、验证结果和未解决事项。
9. 用户反馈结果质量；系统在适当授权下形成可复用证据或改进建议。

## 10. 功能需求与优先级

### F-01 自然语言任务入口（P0）
- 首页核心交互为任务输入框，而不是工具分类导航。
- 支持用户用日常语言描述目标、输出形式和约束。
- 能识别目标、领域、输入、时限和敏感性。
- 对关键缺失信息进行聚焦式澄清。
- 验收：覆盖研究、写作、数据分析、开发、自动化五类代表性任务；用户无需先选择工具即可进入任务规划。

### F-02 能力目录与发现（P0）
- 能力按统一 Manifest 解析，展示名称、用途、适用任务、输入输出、来源仓库、路径、Commit、许可证、状态和风险。
- 支持知识、框架、Prompt、脚本、工具、Agent、工作流、案例、数据集和模型适配器等类型。
- 支持关键词、标签、领域、任务意图和兼容条件筛选。
- 显示来源和最后同步时间；索引故障不能伪装成空目录。
- 验收：目录记录可追溯到不可变 Commit SHA 和仓库路径；删除或改名文件后索引可正确更新。

### F-03 能力解释与比较（P0）
- 用普通用户语言解释能力能做什么、不能做什么、适合谁、需要什么输入。
- 展示证据等级、验证方式、最后验证时间、许可证、权限和风险。
- 比较候选能力时说明排序理由，不将 GitHub stars 直接解释为质量。
- 验收：用户无需阅读源码即可理解推荐用途、限制和是否可以直接使用。

### F-04 任务规划与能力组合（P1）
- 将任务拆解为有依赖关系的步骤。
- 每个步骤绑定能力、输入输出和成功标准。
- 检查能力间接口、运行环境和依赖兼容性。
- 不确定时允许降级为建议方案、要求补充信息或人工处理。
- 验收：计划结构化、可解释、可检查；不允许仅凭自然语言猜测就宣称能力可执行。

### F-05 安全执行（P1）
- 只允许已审核的适配器和明确支持的执行模式。
- 执行前显示所需权限、数据范围、外部副作用、费用和风险。
- 高风险或不可逆操作必须逐项审批。
- 支持停止执行、超时、资源预算、审计记录和失败处理。
- 验收：未授权操作无法触发；发现阶段不执行代码；所有执行可追踪到来源版本与适配器版本。

### F-06 结果验证与证据（P1）
- 任务启动时尽可能定义成功标准。
- 结果评估包括格式/结构检查、规则检查、测试、事实来源、人工评价或领域专用指标。
- 将模型自评与独立验证区分。
- 显示未验证项和不确定性。
- 验收：每个标记为 verified 的结果都有明确标准、方法、时间和可访问证据。

### F-07 用户反馈与能力进化（P2）
- 收集有上下文的成功/失败反馈。
- 反馈关联能力版本、任务类型和评测标准。
- 形成 GitHub Issue 或 PR 建议前，先去重、脱敏和征得必要授权。
- 不自动把用户私人输入、机密材料或敏感数据发布到公开仓库。
- 验收：每条外部贡献有来源、授权和审查记录。

### F-08 开发者能力发布（P2）
- 开发者通过 Manifest 发布能力，无需迁移到平台专属格式。
- 支持公开仓库只读发现和明确授权的私有仓库接入。
- 展示作者归属、许可证、版本、使用说明和贡献入口。
- 验收：第三方作者可在不改变原有 GitHub 工作流的情况下被平台发现。

### F-09 个人工作台与任务历史（P1）
- 用户可查看任务状态、历史结果、授权记录和反馈。
- 用户可删除或导出其可控的个人数据（策略在实现前定义）。
- 不在公开能力目录中泄露用户任务和私人运行日志。
- 验收：跨用户访问隔离通过自动化测试。

## 11. 信息架构

面向普通用户的一级导航建议：
- **完成任务**：任务入口、进行中任务和历史结果；
- **发现能力**：按任务场景发现已解释、可比较的能力；
- **知识与方法**：原理、框架、教程和知识资产；
- **案例与证据**：真实案例、评测、限制和复现材料；
- **创作者 / 社区**：面向开发者的发布、审核和贡献入口。

Knowledge / Tools / Cases 三库可保留为底层资产分类，但不应强迫普通用户以这三类技术分类开始使用产品。

## 12. 关键页面要求

- 首页：以任务输入为核心；示例任务帮助理解能力边界；不显示伪造实时统计。
- 任务规划页：用户目标、系统理解、澄清问题、推荐能力、排序原因、步骤、数据访问和风险。
- 执行页：步骤状态、进度、暂停审批和停止操作；失败时说明影响和恢复路径。
- 结果页：结果、来源引用、验证标准、未完成事项、反馈和复用入口。
- 能力详情页：先说明任务价值和适用边界，再提供仓库、版本、许可、接口和证据等高级信息。

## 13. 非功能需求

- 移动端优先、响应式布局、键盘可访问；
- 加载、空状态、错误、离线和权限拒绝均有明确反馈；
- API、索引、执行和前端分层，便于替换供应商；
- 关键数据访问和执行动作有审计能力；
- 不将密钥、令牌或用户私密数据写入公开 GitHub；
- 用户任务在刷新、断线或重试时保持一致状态语义。

## 14. MVP 边界

首个端到端 MVP 只做：
1. 只读接入三个自有公开仓库；
2. 解析机器可读 Manifest 和少量明确支持的文档类型；
3. 建立可重建的能力目录与全文检索；
4. 用自然语言描述任务并推荐相关能力；
5. 展示推荐理由、来源、版本、限制和验证状态；
6. 提供人工可执行的任务计划，不运行任意仓库代码。

MVP 不承诺自动执行所有推荐能力。先验证“找到正确能力并让普通人理解”这一核心价值，再逐步开放受控执行。

# 第三部分：技术架构

## 15. 仓库职责

- **AI-Knowledge-Bank**：产品前端、能力目录、来源连接器、检索 API、证据展示、社区和用户体验。
- **cognitive-engine**：任务理解、TaskSpec、规划、能力路由、组合、运行轨迹和评估协议。
- **writing-engines**：专业写作能力、原子操作、领域工作流、语料和应用实验。

三个仓库保持独立版本和发布节奏，通过版本化 JSON Schema / API 契约协作，不使用隐式文件路径耦合。

## 16. 逻辑分层

1. Experience Layer：Web / Mobile、任务入口、计划确认、执行进度、结果和个人工作台。
2. Application API：身份、任务会话、能力查询、审批、反馈和审计接口。
3. Capability Catalog：标准化能力记录、来源映射、版本、状态和过滤。
4. Ingestion & Indexing：GitHub 同步、文件解析、Manifest 校验、全文索引和语义索引。
5. Intelligence Layer：任务理解、检索排序、规划、路由、组合和评估。
6. Runtime Layer：API / MCP / sandbox / human-guided 等受控适配器。
7. Trust & Governance：来源、许可证、安全扫描、权限、审批、审计和生命周期。

## 17. GitHub 内容源

### GitHub 的职责
GitHub 作为知识资产的 canonical source of truth：
- 源文件、文档、代码、Manifest、测试、示例和版本历史；
- Commit SHA、Tag、Release 和作者归属；
- Issue、PR 和 Actions 作为可选协作与自动化机制。

GitHub 不承担：
- 高频事务状态和用户会话；
- 细粒度实时权限判定；
- 搜索排序的在线计算；
- 未经隔离的代码执行；
- 私密用户输入和运行日志的默认存储。

### 连接器接口建议
- registerSource(sourceConfig)
- listChanges(cursor)
- getTree(revision)
- getTextAsset(path, revision)
- getRevisionMetadata(revision)
- getLicenseMetadata(path, revision)
- healthCheck()

GitHubConnector 是首个实现。未来可增加 GitLab、Codeberg、内部 Git 服务或经授权的文档源，而不修改前端和检索 API。

### 同步策略
- 首次同步：读取仓库元数据和树，按白名单文件类型获取文本文件；
- 增量同步：以 Commit SHA / 比较 API / Webhook 事件为依据；
- 幂等键：source_id + path + commit_sha；
- 记录同步状态、游标、最后成功时间和失败原因；
- 对 API 限流、超时和暂时性错误使用指数退避与缓存；
- 对删除、改名和权限变化执行索引 tombstone / 更新；
- 固定文件类型、大小、内容长度限制，避免读取超大或二进制文件；
- 公开仓库默认只读，私有仓库需要显式授权和最小权限。

## 18. 标准能力对象

CatalogRecord 至少包含：
- id、name、kind、description、use_cases、tags；
- inputs、outputs、requirements；
- source.repository、source.path、source.commit_sha、license、publisher；
- lifecycle、verification.status、evidence；
- execution.mode、adapter_id、permissions、risk；
- created_at、updated_at、indexed_at。

Manifest 是作者声明；平台解析结果是目录数据；平台验证结果是独立证据。三者必须区分，不能把作者自述自动升级为平台认证。

## 19. 索引与检索

### 首期
- Manifest 元数据过滤；
- 标题、描述、README 和白名单文本的全文检索；
- 标签、任务类型、语言、能力类型和风险过滤；
- 可解释的确定性排序。

### 后续
- 文本切片和 Embedding；
- 向量召回 + 关键词召回；
- Reranker 重排；
- 用户任务与能力输入输出契约的兼容性匹配；
- 质量、证据、时效、成本和风险的多目标排序。

排序至少保留 task relevance、input/output compatibility、verification strength、source freshness、execution availability、license/policy eligibility、risk and cost penalties。推荐理由应可展示。未验证能力可被发现，但必须明确标注。

## 20. API 契约建议

以下是目标 API 草案，实际路由以实现时的版本化契约为准：
- GET /api/v1/capabilities：分页、过滤、排序能力目录；
- GET /api/v1/capabilities/{id}：能力详情和来源版本；
- POST /api/v1/search：自然语言 / 关键词检索；
- POST /api/v1/tasks/interpret：将用户目标转为 TaskSpec 草案；
- POST /api/v1/tasks/plan：生成候选能力组合计划；
- POST /api/v1/tasks/{id}/approvals：记录明确审批；
- POST /api/v1/tasks/{id}/runs：启动已允许的执行计划；
- GET /api/v1/tasks/{id}：任务状态和结果；
- POST /api/v1/feedback：任务或能力反馈；
- POST /api/v1/sources/github/sync：受权限保护的同步触发。

所有 API 需定义请求/响应 Schema、错误码、鉴权、幂等策略、分页和速率限制。不得仅凭本文件视为上述 API 已实现。

## 21. Cognitive Engine 集成

AI Knowledge Bank 向 Cognitive Engine 传递结构化 TaskSpec，而不是直接拼接未经验证的仓库文本作为执行指令。

跨仓库契约建议：
- TaskSpec：目标、上下文引用、输入、约束、成功标准、风险偏好；
- CandidateCapability：能力 ID、来源 revision、接口、许可和证据；
- RoutingDecision：选择原因、未选择候选项、置信度和约束；
- ExecutionPlan：步骤、依赖、输入输出绑定、审批点和预算；
- ExecutionTrace：步骤状态、适配器版本、时间、资源和错误；
- EvaluationReport：成功标准、测试、证据、未解决问题和结论。

契约需要版本化、向后兼容测试和示例 Fixture。

## 22. 运行时设计

所有执行必须经 allowlisted adapter：
- instruction：只提供说明，不宣称自动执行；
- api：调用经过登记的 API；
- mcp：使用受控 MCP 连接和工具权限；
- sandbox：在隔离环境执行固定镜像或经审查制品；
- human-guided：由用户完成关键步骤，平台提供指导。

执行时绑定不可变来源 Commit、Adapter 版本和策略版本。禁止把仓库默认分支 HEAD 当作长期可复现的执行版本。

## 23. 数据分类与存储

| 数据 | 权威来源 / 存储 | 可否重建 |
| --- | --- | --- |
| 文档、代码、Manifest、测试 | GitHub | 原始资产不由索引替代 |
| 来源 Commit、Release | GitHub 元数据 | 可重新读取 |
| 搜索目录、全文索引、向量 | 派生索引存储 | 必须可重建 |
| 用户身份、授权 | 身份服务 | 不从公开 GitHub 推导 |
| 任务状态、审批、运行轨迹 | 受控运行数据存储 | 按保留策略归档 |
| 缓存、限流计数 | Cache / KV | 可重建 |
| 公开评测集和能力测试 | GitHub | 版本化 |
| 用户私人反馈 | 受控数据存储 | 不默认公开 |

因此，GitHub-native 不意味着完全不需要数据库。目标是去掉重复维护的知识资产数据库，而不是取消运行系统必需的事务状态。

## 24. 可观测性与部署

- 为每个同步、搜索、规划和执行请求生成 correlation_id；
- 记录延迟、错误率、限流、索引滞后和运行成本；
- 监控来源同步成功率、文件解析失败率、目录新鲜度；
- 监控检索 Recall@K / NDCG 等离线指标，以及任务成功率等在线指标；
- 对外部依赖失败提供降级行为和清晰用户提示；
- 不把空响应、权限错误和同步失败统一显示为“没有结果”。

环境划分：
- Local：本地开发、Fixture 和模拟连接器；
- CI：类型检查、Lint、单元测试、Schema 验证、契约测试和构建；
- Preview：PR 预览和只读集成测试；
- Production：独立配置、最小权限、密钥管理、审计和回滚。

Oracle VM、Azure、Supabase 等现有资源是否继续使用，应由容量、成本、安全和运维评估决定；不得因为本架构文档而自动创建资源、改动生产配置或执行数据库迁移。

# 第四部分：安全与信任

## 25. 基本安全原则

**发现不等于信任；信任不等于执行授权。**

主要风险包括恶意仓库、Prompt Injection、恶意脚本和依赖投毒、伪造能力描述、许可证冲突、凭据泄露、越权调用、数据外传、资源耗尽、Agent 外部副作用、过期能力和虚假验证标记。

## 26. 信任维度

采用彼此独立的维度，而非单一可信分数：

### 来源状态
- unknown；
- source-identified；
- publisher-claimed；
- publisher-verified（实现后）。

### 内容审核状态
- unreviewed；
- automated-check-passed；
- human-reviewed；
- rejected / disputed。

### 任务验证状态
- unverified；
- tested；
- verified；
- expired / disputed。

### 执行资格
- not-executable；
- adapter-approved；
- permission-approved；
- executable-under-policy。

仓库可追溯不等于代码安全，测试通过不等于适合所有任务。

## 27. 来源、许可和解析安全

- 记录仓库 URL、路径、Commit SHA、作者/发布者声明和许可证；
- 许可证未知时明确显示 unknown，不推断可再分发或可执行；
- 尊重许可证义务、版权、商标和原作者归属；
- 无法确认许可的内容限制复制和再分发，优先展示来源链接和必要元数据；
- 仓库文件视为不可信输入；
- ingestion 阶段只解析，不执行代码、脚本、构建任务或安装依赖；
- 对文件类型、大小、深度、编码、归档展开和解析时间设限；
- 对提示注入、外部链接、隐藏指令和敏感信息模式进行检测；
- 检索内容始终作为数据，不得覆盖系统策略或工具授权。

## 28. 执行安全

- 只允许显式登记的 Adapter；
- 每个 Adapter 定义权限、网络、文件系统、密钥、资源预算和超时；
- 沙盒默认无网络、只读文件系统和最小资源；
- Secrets 通过专用密钥服务注入，不写入 Manifest、日志或模型上下文；
- 执行绑定不可变 Commit SHA 和 Adapter 版本；
- 运行中支持取消、超时和异常终止；
- 网络域名采用 allowlist；禁止默认任意外联；
- 对依赖进行锁定和供应链检查；
- 禁止将发现的任意 GitHub Action、脚本或容器直接作为执行入口。

## 29. 用户授权等级

- L0：公开信息读取和纯检索；
- L1：用户明确提供的文件或数据分析；
- L2：调用已授权的第三方 API / 账户读取数据；
- L3：向外部系统写入、发布、发送或修改数据；
- L4：涉及资金、法律承诺、生产基础设施、删除数据或其他高影响行为。

L2 以上应明确显示数据范围和授权来源；L3/L4 必须在操作发生前进行清晰、具体的确认。对不允许自动化的行为应拒绝或转为人工指导。

## 30. 证据与隐私

- 区分发布者声明、自动化测试、独立评测和真实用户反馈；
- 每条验证证据绑定能力版本、测试版本、日期和环境；
- 过期证据应降级；
- 模型自评不能单独作为 verified 的充分依据；
- 只收集完成任务所需数据；
- 默认不将用户任务输入、文件和执行日志公开写入 GitHub；
- 日志脱敏，不记录密钥、认证头和不必要的个人信息；
- 定义任务数据保留、删除、导出和访问控制策略；
- 用于公开案例或能力改进的数据必须有明确授权和脱敏流程。

## 31. 安全验收清单

- [ ] 恶意 Manifest / README / Prompt Injection 测试；
- [ ] 未知许可证和许可证冲突处理；
- [ ] GitHub Token 最小权限、轮换和撤销；
- [ ] 文件大小、解析时间和资源耗尽保护；
- [ ] 依赖锁定和供应链扫描；
- [ ] 越权、跨用户访问和私有仓库隔离测试；
- [ ] 外部副作用审批和重复请求幂等测试；
- [ ] 沙盒逃逸和网络策略测试；
- [ ] 日志脱敏和数据保留验证；
- [ ] 执行停止、超时、失败恢复和审计追踪。

# 第五部分：能力贡献规范

## 32. 开发者贡献原则

开发者继续在自己的 GitHub 仓库中工作。AI Knowledge Bank 通过标准 Manifest 发现和解释能力，不要求作者迁移源码或放弃原有发布流程。

Manifest 是能力目录的机器可读入口，不是执行许可，也不是平台认证。

## 33. 推荐目录结构

仓库可采用以下结构；无需为了接入平台强制重排既有项目：

    repository/
      README.md
      LICENSE
      capabilities/
        capability-id/
          capability.json
          README.md
          examples/
          tests/
          eval/

若仓库已有 registry/index 文件，可由适配器读取，不要求重复复制完整资产。

## 34. Manifest 与描述要求

使用仓库 schemas 目录中的 capability-manifest.schema.json 作为初始规范。

最低必需字段：
- schema_version；
- 稳定 id；
- name、kind、description；
- source.repository、source.path；
- lifecycle。

建议完整填写：
- use_cases、tags、languages；
- inputs、outputs；
- requirements；
- execution.mode、adapter_id、permissions、risk；
- verification.status、method、success_criteria、evidence；
- version、updated_at。

环境变量只列名称，不得在 Manifest 中写入任何密钥值。

优秀说明应回答：
1. 它解决什么具体问题？
2. 适合哪些任务和用户？
3. 需要什么输入，输出什么结果？
4. 使用前需要哪些依赖和前置条件？
5. 已知限制、失败模式和不适用场景是什么？
6. 如何验证输出质量？
7. 许可证和来源是什么？

避免“最强”“100% 准确”“适合所有场景”等无法验证的宣传性表述。

## 35. 版本、验证与发布

- 每次索引记录应绑定 Commit SHA；
- 发布者可提供 SemVer 或其他版本标签；
- 破坏性接口变化应提升主版本或声明迁移说明；
- 过期、撤销或不再维护的能力应标注 deprecated；
- Fork 必须保留上游来源和修改归属；
- 验证证据应说明测试环境、能力版本、日期、方法和局限；
- 仅有 README 自述或 GitHub stars 不足以构成 verified 证据。

Manifest 中声明 execution.mode 仅表示作者建议或实现接口。平台仍须独立审核 Adapter、依赖、权限、许可证和安全策略。

## 36. 发布检查清单

- [ ] 能力 ID 稳定且不冲突；
- [ ] Manifest 通过 Schema 校验；
- [ ] 描述明确、无夸大承诺；
- [ ] 输入输出和依赖清晰；
- [ ] LICENSE 存在且兼容；
- [ ] 来源和作者归属准确；
- [ ] 测试和证据可访问；
- [ ] 风险、权限和网络需求如实声明；
- [ ] 未提交 Secrets、个人数据或受限内容；
- [ ] 版本和维护状态明确。

# 第六部分：长期开发路线图

## 37. 阶段推进原则

按可验证里程碑推进，不以日历日期替代完成标准。每个阶段必须具备范围、依赖、交付物、自动化测试、人工验收、风险记录和退出标准。前一阶段退出标准未满足，不进入高风险的自动执行阶段。

## Phase 0 — 产品与架构基线

目标：对产品方向、仓库边界、能力描述和安全原则达成一致。

交付：
- 项目章程、PRD、技术架构、路线图、安全模型；
- Capability Manifest Schema v1；
- 三仓库职责和接口边界；
- ADR 机制和文档治理规则。

退出标准：
- 核心团队能够用同一套定义解释产品；
- Schema 有正反例和自动化验证；
- 关键数据分类和执行安全边界明确。

## Phase 1 — GitHub 只读接入与能力目录 MVP

目标：将自有三个仓库中的能力资产自动发现并标准化。

范围：
- GitHub 公开仓库只读连接；
- 首批来源：AI-Knowledge-Bank、cognitive-engine、writing-engines；
- 仓库树、Manifest、README 和受支持文本格式解析；
- 来源 Commit 固定、许可证元数据、同步状态；
- 能力目录、分页、全文搜索和基础过滤；
- 失效、删除、改名、限流和同步错误处理。

交付：
- GitHub Source Connector；
- Manifest parser / validator；
- normalized catalog；
- ingestion job 和 sync status；
- 只读 Catalog API；
- 数据样本和端到端测试。

退出标准：
- 可重复执行全量和增量同步；
- 相同 revision 不产生重复记录；
- 所有目录项可追溯到仓库、路径和 Commit SHA；
- 删除文件、改动 Commit、无效 Manifest 和 API 限流均有测试；
- 不执行任何发现的仓库代码。

## Phase 2 — 普通用户任务入口与能力发现

目标：让不懂 GitHub 的用户能用自然语言找到、理解并判断能力。

交付：
- task-first 首页和移动端体验；
- 任务分类与意图提取；
- 关键词 + 元数据检索；
- 推荐卡片、解释、来源和证据状态；
- 任务澄清；
- 能力详情、限制、许可证和兼容性展示；
- 用户任务样本和检索离线评估。

退出标准：
- 代表性用户能在不打开 GitHub 的情况下完成发现流程；
- 对基准任务达到预先定义的 Recall@K / NDCG 门槛；
- 不把未经验证能力标记为 verified；
- 空状态、错误状态和移动端体验通过验收。

## Phase 3 — Cognitive Engine 任务规划与能力组合

目标：从推荐资源升级为生成完整任务方案。

交付：
- TaskSpec / CandidateCapability / RoutingDecision / ExecutionPlan 契约；
- 与 Cognitive Engine 版本化集成；
- 能力输入输出兼容性；
- 多步骤依赖和失败路径；
- 计划解释、置信度和人工确认；
- 基准任务集和对照实验。

退出标准：
- 计划步骤可检查、可解释；
- 每个步骤能追溯能力版本；
- 不兼容输入输出被识别；
- 不确定时能够澄清、拒绝或人工升级；
- 在代表性任务集上优于仅模型直接回答的基准。

## Phase 4 — 安全执行 MVP

目标：对有限、低风险能力实现端到端执行。

交付：
- Adapter Registry；
- 沙盒或受控 API / MCP 执行；
- Secret 管理和最小权限；
- Approval Gate；
- 预算、超时、取消和审计；
- ExecutionTrace；
- 失败恢复和安全测试。

退出标准：
- 未授权调用无法发生；
- 不会因仓库被发现而自动运行其代码；
- 高风险和外部副作用均有明确审批；
- 运行可停止、可审计；
- 安全测试和故障注入通过。

## Phase 5 — 评估、证据与能力进化

目标：建立可持续改进的质量反馈闭环。

交付：
- Evaluation Framework；
- 能力级和任务级评测；
- 证据来源、复现条件和时效；
- 用户反馈和问题去重；
- GitHub Issue / PR 建议工作流；
- 过期能力、争议能力和撤销机制。

退出标准：
- verified 状态对应可审计证据；
- 评估与模型自评明确区分；
- 用户私人数据不会未经授权进入公开仓库；
- 版本升级可比较、可回滚；
- 反馈确实推动质量指标改善。

## Phase 6 — 开放生态与规模化

目标：从自有仓库扩展到全球开发者生态和组织能力网络。

方向：
- 更多 Git 平台和公开来源；
- 开发者发布、认领、维护和分析工具；
- 私有组织仓库和团队空间；
- 能力使用配额、成本透明和商业模式；
- 多语言、多地区和多租户治理；
- 能力市场与第三方服务合作。

退出标准：
- 多来源接入不破坏统一目录和信任模型；
- 创作者归属、许可证和下架机制有效；
- 多租户隔离和审计经过安全验证；
- 单位成功任务成本可控；
- 生态增长伴随质量和任务成功率提升。

## 38. 每个迭代的标准流程

1. 更新需求与用户任务；
2. 明确本次不做什么；
3. 检查架构边界和依赖；
4. 编写验收标准和测试；
5. 在独立分支开发；
6. CI、代码审查和安全检查；
7. Preview / 测试环境验证；
8. 更新文档、风险和路线图；
9. 由项目负责人决定是否合并和发布。

每项工作至少记录 ID、标题、所属阶段、用户价值、优先级、状态、依赖、验收标准、测试证据 / PR / Issue、风险与决策记录。

优先级：
- P0：影响安全、核心任务闭环、数据正确性或阶段退出标准；
- P1：显著改善核心用户旅程、检索质量或开发效率；
- P2：规模化、生态、商业化和非核心体验增强。

不以功能数量作为阶段进度。阶段完成必须由退出标准和证据支持。

# 第七部分：项目治理与架构决策

## 39. 文档与决策治理

- 本文档集是持续演进的项目基线，不代表所有阶段均已实现。
- 每项能力标注状态：planned、in progress、implemented、verified、deprecated。
- 重大架构变化必须新增 ADR（Architecture Decision Record），说明背景、备选方案、决策、代价和迁移方式。
- 代码、自动化测试和运行证据优先于文档中的完成声明。
- 每个里程碑结束时更新路线图、已知问题、风险和下一阶段入口。

## 40. ADR-0001：GitHub 作为首要能力资产权威来源

状态：Accepted as initial direction。

背景：若平台自行复制和维护所有知识、代码与工具，会产生双重维护、版本漂移、来源不清和协作成本。开发者已在 GitHub 上维护大量可追溯资产。

决策：
1. 首期以 GitHub 作为能力资产的首要 canonical source。
2. 能力源文件、Manifest、测试、示例和版本历史由原始仓库维护。
3. 平台只构建可重建的目录和检索索引，并保留仓库、路径、Commit SHA 和许可证。
4. GitHub 不承担用户会话、审批、实时执行状态、私密运行日志或沙盒执行。
5. 通过 SourceConnector 抽象来源，避免未来锁定 GitHub。

备选方案：
- 自建数据库复制全部知识：拒绝，容易造成双重权威和同步漂移。
- 仅展示 GitHub 链接：拒绝，不能满足普通用户理解、检索和使用的需求。
- 完全取消所有数据库：拒绝，任务状态、权限、审计和实时事务仍需要受控运行存储。

后果：
- 正面：版本与归属清晰、降低知识资产维护成本、开发者无需迁移工作流、索引可重建。
- 代价：GitHub API 限流和可用性、非结构化仓库解析成本、许可证与恶意内容风险、运行时数据仍需要其他存储。

复审条件：多来源接入、私有仓库、数据驻留、API 限额或商业条款发生变化时重新评估。

# 附录 A：自我应用式工程方法（Dogfooding as Validation）

## A.1 基本原则

AI Knowledge Bank 的开发过程必须使用其自身倡导的能力发现与复用方法。平台不是等到开发完成后才寻找验证场景；**平台自身的真实工程任务就是第一个持续运行的验证场景**。

> Reuse before Build. Discover before Integrate. Evidence before Trust. Compose before Monolith. Learn from Every Execution.

这意味着每项非平凡工程任务，在决定自研之前，应先从 GitHub 等开放生态发现候选工具、库、Agent、工作流和知识资产；评估其功能匹配、维护状态、许可证、安全性、兼容性、集成成本与验证证据；再决定直接复用、组合、自研补缺或暂不采用。

## A.2 标准工程闭环

1. **Task intake**：定义工程目标、输入、约束和验收标准。
2. **Capability discovery**：从 GitHub 和其他获准来源发现候选能力，记录不可变版本与来源。
3. **Capability assessment**：评估功能适配、维护活跃度、许可证、依赖、安全风险、接口兼容性和总拥有成本。
4. **Selection and composition**：说明采用、组合、自研或拒绝的理由；识别能力之间的输入输出和依赖关系。
5. **Authorized integration**：仅通过明确的依赖、适配器和权限边界接入；不执行未知仓库代码或安装未审查依赖。
6. **Task-level verification**：用测试、基准、人工评审或领域指标验证真实结果，不把 README 声明、Stars 或模型自评当作证据。
7. **Capability learning**：记录版本、适用范围、失败模式、成本、证据和复用建议；未经授权不得把私人任务输入或日志发布到公开仓库。

## A.3 决策规则

每项候选能力至少检查：

- **功能适配**：是否解决当前明确的子问题，而不是只在名称上相似；
- **维护与兼容性**：最近维护情况、发布版本、运行时、依赖和 API 稳定性；
- **许可证与归属**：许可证是否明确、是否允许目标用途、是否需要保留声明；
- **安全与权限**：是否执行代码、访问网络、读取文件、处理凭证或产生外部副作用；
- **质量证据**：测试、基准、独立评估、可复现案例和已知失败模式；
- **集成总成本**：接入、维护、迁移、性能、运行费用和锁定风险。

决策结果统一为：`reuse`、`compose`、`adapt`、`build_gap`、`defer` 或 `reject`，并记录理由与证据。

## A.4 安全边界

- 发现不等于信任，信任不等于执行授权。
- 默认只读分析公开仓库；禁止在导入阶段执行源码、脚本、Prompt 或 Agent 指令。
- 未明确核实许可证的能力保持 `review_required`，不得标记为可自由复用。
- 第三方工具必须通过显式适配器、最小权限、沙箱和用户授权后才能执行。
- 用户输入、私有文件、运行日志和凭证不得自动进入公开 GitHub 仓库。
- GitHub 负责版本化源资产；任务会话、授权、执行状态和私人反馈由受控运行时存储管理。

## A.5 首个自我验证工程

Phase 1.2 — GitHub Capability Discovery & Read-only Reuse：

- 使用固定 Commit SHA 对三个核心仓库进行可重复的只读解析；
- 将 17 个写作引擎、182 个原子能力、认知引擎中的对应 182 条领域 Primitive、4 条通用推理 Primitive，以及 AKB 明确的种子记录映射到统一 Manifest；
- 将 182 条领域 Primitive 与 Atom Index 做一对一 ID 对账，不重复计数；
- 保留源仓库、Commit SHA、Blob SHA、路径、Anchor、许可证状态、Parser 版本和内容指纹；
- 生成确定性本地目录与机器可读报告，不写生产数据库；
- 对发现、解析、规范化、去重、来源追溯和安全边界建立自动化测试；
- 以真实开发任务评估“先发现并复用”相较“直接自研”的时间、质量、成本和维护负担。

本阶段完成标准不是“导入脚本能够运行”，而是来源可追溯、记录可对账、重复运行结果稳定、错误不会静默丢失、没有未授权代码执行，并能据此决定下一步的检索与编排设计。

# ADR-0002 摘要：Reuse Before Build

**决策：** 所有非平凡工程任务先发现和评估已有能力，再决定复用、组合、适配、暂缓或建设能力缺口。Cognitive Engine 必须在内部 Primitive 路由之前执行这一决策；许可证、安全、验证或兼容性未明的候选应触发暂缓，而不是被默认采用或直接忽略。

平台必须区分发现、信任和执行授权。复用决策不执行任何第三方代码；真正执行仍须经过 Adapter、最小权限、沙箱、预算与审批。复用率只作为诊断指标，任务成功率、质量、成本和安全是约束条件。完整决策见 [ADR-0002](ADR-0002-REUSE-BEFORE-BUILD.md)。
